It proxies to one endpoint and nothing else:

  Agent   {{ .Values.agent.url }}  (turn budget {{ .Values.agent.timeout }})

/readyz here reports the AGENT's readiness, forwarding its message verbatim, so a
503 still names whether Ollama or the MCP server is the one that failed:

  curl -s http://$NODE:{{ .Values.service.nodePort | default "<nodeport>" }}/readyz

Two things worth knowing before the first question:

  * Answers are not streamed. One turn blocks for 30-180s and the page shows a
    running count while it waits. That is normal, not a hang.
  * Conversations live in the browser, not here. The agent's /chat is stateless,
    so the page replays the transcript each turn and "New chat" is purely local.
    Clearing site data clears the history; a pod restart does not.

This release grants the UI NO Kubernetes permissions -- it talks to fathom-agent
over HTTP and to nothing else, and the pod mounts no token. This should print
nothing but a warning:

  kubectl auth can-i --list \
    --as=system:serviceaccount:{{ include "fathom-front.namespace" . }}:{{ include "fathom-front.serviceAccountName" . }}
